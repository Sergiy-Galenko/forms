# Excel, публічні тести й обмеження

Реалізовано імпорт `.xlsx` з перевіркою рядків, шаблон і preview, ключі відповідей/бали, серверну публікацію, проходження за спільним URL, особистий результат і відповіді у статистиці автора. Збережено CRA, JS та всі наявні маршрути.

## Перевірки

- `CI=true npm run build` — успішно, без warnings.
- `npx eslint src --ext .js --max-warnings=0` — успішно.
- Frontend: 22 тести (наявний UI/сторінки, 8 форматів відповідей, імпорт чисел/дат і коректна відповідь 0).
- API: 10 тестів — відокремлений учасник/автор, оцінювання, секрети, пароль, дедлайн, закриття, конкурентний глобальний ліміт, повтори, cookie-обмеження, зміна конфігурації, повтор конфліктного запису та збереження файлу після нового екземпляра сервера.
- Реальний Chrome: завантажено Excel-шаблон через file input, створено тест із 3 питаннями, опубліковано з паролем і лімітом 1.
- Новий browser context: неправильний пароль відхилено, правильний відкриває питання; після відповіді результат **4/4**.
- Третій browser context: після першої відповіді доступ заблоковано глобальним лімітом.
- Автор у своєму context отримує відповіді у статистиці.
- На 320 px у dark theme немає горизонтального скролу чи pageerror.
- axe: 0 A/AA violations у preview імпорту, налаштуваннях поширення та публічному тесті на 320 px.

## Розгортання

Це локальна наскрізна перевірка з файловим адаптером. Vercel-команда не надала доступ поточному підключенню: API двічі повернув 403. Хмарне сховище не створювалося, змінні та production-деплой не змінювалися. Для роботи загальнодоступного сайту потрібні Upstash Redis, серверні змінні з `.env.example` та розгортання нової версії. Redis REST/CAS інтеграція підготовлена; live-тест із реальним Redis до підключення не проводився.

Робочі посилання не імітуються URL-фрагментами з усіма питаннями або правильними відповідями. Якщо backend не готовий, користувач отримує помилку публікації, а чернетка залишається локально.

## Важливі межі

- Одна відповідь на браузер — cookie-обмеження, а не гарантія однієї людини. Для ідентифікованих учасників потрібне окреме завдання з акаунтами/запрошеннями.
- Ключ керування — випадкова 256-бітна capability, зберігається у браузері автора; на сервері лише хеш. Відновлення після втрати локальних даних не реалізоване.
- Перший аркуш, до 2 МБ та 200 питань. Макроси, `.xls`, картинки й довільні макети без колонок не імпортуються.
- Вільні відповіді перевіряються збігом, не семантичним аналізом.
- Файловий адаптер призначений тільки для одного локального процесу. У production використовується Redis REST із атомарним compare-and-swap та повторною перевіркою лімітів.
- Загальний запис одного тесту з відповідями обмежений 4 МБ; після досягнення межі API відхиляє нові відповіді зрозумілою помилкою. Додатково діють ліміти обраного провайдера сховища.
- Чинні дані `forms` не мігруються: нові поля `correctAnswers`, `points` та `publication` додаються до нових/відредагованих записів. Наявні форми без ключів залишаються опитуваннями без оцінювання.

## Технічні джерела

- [read-excel-file: browser API](https://github.com/catamphetamine/read-excel-file#read-excel-filebrowser) — вузька залежність для справжнього `.xlsx`; основний reader-чанк приблизно 16,5 kB gzip і не входить у початкове завантаження.
- [Vercel Node.js Functions](https://vercel.com/docs/functions/runtimes/node-js) — серверна точка входу `api/tests.js`.
- [Upstash REST API](https://upstash.com/docs/redis/features/restapi) та [Redis EVAL atomicity](https://redis.io/docs/latest/develop/programmability/eval-intro/) — серверне сховище й конкурентні перевірки лімітів.
